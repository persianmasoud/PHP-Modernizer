# Session 006

Date:
2026-08-05

Title:
Rule Engine Design and Modernization Knowledge Model Discussion

## Objective

Define the future architecture of the PHP Modernizer Rule Engine.

The goal is to create a flexible migration knowledge system that is not limited to detecting PHP compatibility issues.

## Background

The Analyzer currently detects technical issues.

However, real legacy modernization requires more than detection.

A complete modernization process needs:

* Understanding the issue
* Evaluating risk
* Providing migration guidance
* Supporting safe changes

## Analyzer vs Rule Engine

Decision direction:

Analyzer and Rule Engine must have separate responsibilities.

Analyzer:

* Collects technical information
* Detects patterns
* Finds possible issues

Rule Engine:

* Applies modernization knowledge
* Evaluates rules
* Determines recommendations
* Defines migration strategies

## Rule Concept

A Rule represents migration knowledge.

A Rule should describe:

* What is detected
* Why it matters
* Which versions are affected
* What should be done
* How changes should be handled

## Rule Categories

Initial categories:

* PHP Compatibility
* Security
* Database
* Charset
* Configuration
* Architecture Modernization
* Quality Improvement

## Severity Model

Severity should represent risk level.

Color visualization will be based on Severity, not Category.

Levels:

* Critical
* High
* Medium
* Low
* Info

Severity affects:

* Report visualization
* Migration priority
* Auto-fix permissions
* Human confirmation requirements

## Rule Dependencies

Some rules depend on other rules.

Example:

PHP Version Detection

↓

Compatibility Rules

↓

Migration Rules

↓

Fix Rules

The Rule Engine must support dependency management.

## Execution Order

Rules may require a specific execution sequence.

The engine should be able to control execution order.

## Rule Conflicts

Some rules may produce conflicting recommendations.

The architecture should support conflict detection.

## Additional Rule Metadata

Future Rule model may include:

* Priority
* Confidence Level
* Evidence
* Migration Phase
* Fix Strategy
* Validation Method
* Reversibility

## External Rule Packs

The project should consider external rule definitions.

Possible future:

* Core Rules
* Community Rules
* Custom Rules

## Architecture Modernization

PHP Modernizer should not only check compatibility.

It should help identify:

* Mixed responsibilities
* Poor separation
* Possible modules
* Legacy architecture patterns

## Module Discovery Concept

Future rules may identify candidates for modularization.

Example:

Customer related files:

* customer.php
* customer_edit.php
* customer_save.php

Possible result:

Customer Module

## Conclusion

PHP Modernizer is moving toward a Migration Knowledge Platform.

The Rule Engine will become the knowledge layer that connects analysis with modernization guidance.
